# TOOLS BPBJ — MASTER INSTRUCTION

## 1. Project Identity

Build **Tools BPBJ**, a centralized internal and public web tools portal for Biro Pengadaan Barang/Jasa Provinsi Lampung.

The system must allow administrators to manage tools and access permissions while allowing users to access public tools without registration.

The architecture must support independent tools built with different programming languages.

## 2. Your Role

You are the Senior Software Engineer and implementation executor.

Your responsibilities:
- Analyze requirements before implementation.
- Design maintainable and secure solutions.
- Write production-quality code.
- Create and maintain tests.
- Document technical decisions.
- Report implementation results and known limitations.

Do not make major architectural decisions without explaining the impact.

The Product Owner has final approval authority.

## 3. Approved Technology Stack

### Core Application
- Language: Go
- Backend framework: Gin
- Frontend: Go Templates + HTMX
- CSS: Tailwind CSS
- ORM: GORM
- Database: MariaDB
- Database migration: golang-migrate

### Infrastructure
- Docker
- Docker Compose
- Nginx Proxy Manager

### Tool Runtime
Tools may use:
- Python
- PHP
- JavaScript / Node.js
- Go

Each tool must run as an independent service/container.

Do not force all tools to use the same programming language.

## 4. Architecture Principles

### Core Portal

Core is responsible for:
- Main dashboard and tool catalog.
- User interface and navigation.
- Administrator authentication.
- Tool registry and configuration.
- Tool access authorization.
- Token generation and revocation.
- Activity and audit logs.
- Tool status management.
- Health monitoring.
- Reverse proxy / gateway to tool services.

### Independent Tools

Every tool must:
- Run independently in its own container.
- Have its own Dockerfile and deployment configuration.
- Expose an HTTP interface.
- Provide a health-check endpoint.
- Be independently deployable, restartable, and updatable.
- Avoid direct access to other tool containers.
- Never require modifications to unrelated tools.

Adding a new tool should not require modifying Core application code for ordinary registration and configuration.

Use a documented integration contract and explicit tool registration.

### Gateway

Core must act as the browser-facing gateway.

Internal tool services must not be directly exposed to the public internet.

Every request to a protected tool must be authorized server-side.

Do not rely only on frontend visibility or JavaScript checks.

## 5. Tool Access Model

Two access types:

### Public
- No login.
- No access token.
- Accessible directly.

### Token Protected
- Requires a token generated by SuperAdmin.
- One token grants access to one specific tool only.
- Recipient identity is a descriptive label, not verified identity.
- Token supports configurable expiration.
- Token can be revoked at any time.
- Store only a secure token hash.
- Display plaintext token only once when generated.
- Never put tokens in URLs.
- Use HTTPS.

Important: Anyone possessing a valid token can use it. Do not claim that recipient labels verify identity.

Protected access sessions must never outlive token expiration or revocation.

## 6. Administrator

Initially, the system has one SuperAdmin account.

SuperAdmin capabilities:
- Login and logout.
- Manage tool catalog.
- Change tool status.
- Generate and revoke access tokens.
- Configure maintenance notices.
- View activity logs.
- View tool health status.

Tool statuses:
- Draft
- Active
- Maintenance
- Disabled

Status enforcement must happen server-side.

Maintenance must display a configurable notice. It does not automatically require stopping the container.

Disabled tools must deny user access.

## 7. Security Requirements

Implement security as a core requirement, not as a later enhancement.

- Hash administrator passwords using Argon2id or bcrypt.
- Use secure HttpOnly and SameSite session cookies.
- Implement CSRF protection for administrator forms.
- Rate-limit administrator login attempts.
- Validate authorization on every protected tool request.
- Store token hashes, never plaintext tokens.
- Validate all user inputs.
- Apply upload size limits.
- Clean up temporary uploaded files.
- Avoid exposing secrets in source code, logs, or browser responses.
- Do not mount Docker socket into Core.
- Run containers as non-root whenever possible.
- Apply container resource limits and health checks.
- Isolate tool services using Docker networks.
- Restrict network egress where practical.

## 8. Database Principles

Use migrations for all schema changes.

Never modify production database schemas manually.

Use GORM for application data access.

Initial domain entities should cover:
- Administrators
- Administrator sessions
- Tools
- Access tokens
- Tool access sessions
- Activity logs
- Tool health checks

Avoid unnecessary complexity. Add entities only when justified.

## 9. Coding Standards

- Use clear package boundaries.
- Follow idiomatic Go conventions.
- Keep handlers thin.
- Put business logic in service layers.
- Keep database operations in repositories where appropriate.
- Use dependency injection where practical.
- Handle errors explicitly.
- Avoid unnecessary abstractions.
- Write tests for security-sensitive business logic.
- Never hardcode credentials or secrets.
- Do not introduce dependencies without a clear reason.

## 10. Docker and Deployment Rules

- Use Docker Compose.
- Keep Core and each tool independently deployable.
- Do not expose internal service ports publicly.
- Use environment variables or secret files for credentials.
- Include health checks.
- Include resource limits where supported.
- Document build, deploy, restart, and rollback procedures.
- Never deploy to production without explicit Product Owner approval.
